# Credaryn Milestone Execution Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Execute exactly one phase at a time. Do not start the next phase until the current phase's STOP gate has been manually verified and explicitly released by the user.

**Source of truth:** [`complete-product-specification-architecture-implementation-roadmap.md`](../../../complete-product-specification-architecture-implementation-roadmap.md), especially Sections 18–26.

**Goal:** Turn the locked Credaryn specification into a sequential, test-first implementation that proves the V1 digital/Paper Seal product, grows it through V2 enterprise interoperability, adds the isolated V3 physical-document intelligence sidecar, and finishes with a documented project-completion audit at Milestone 12.

**Architecture:** Credaryn is a standards-first TypeScript/Node orchestration layer. `@credaryn/core` owns the normalized descriptor, trust policy, validation and verdict model; `@credaryn/node`, `@credaryn/pdf`, `@credaryn/paper` and `@credaryn/verifier` compose those contracts without exposing provider-specific or Java/DSS types. Browser printing, cloud/HSM providers, TrustVC, lifecycle services and OCR are adapters or optional delivery surfaces around the same signed-claim and normalized-verification boundaries.

**Tech Stack:** Node.js 24 LTS, TypeScript 7 strict mode, pnpm 12 workspaces, Vitest 5, fast-check, Puppeteer for server-side controlled PDF generation only, European Commission DSS 6.5 in an isolated Docker adapter, QR + Base45 + deterministic CBOR + COSE_Sign1 + ES256, PostgreSQL only for optional status/admin persistence, TrustVC for V2 W3C interoperability, and Python with PaddleOCR PP-OCRv6/PP-StructureV3 for V3.

## Global Constraints

These requirements are copied from the locked implementation baseline and apply to every phase:

- Runtime baseline: Node.js 24 LTS.
- Language: TypeScript 7 with strict mode and no implicit any.
- Package manager: pnpm 12 workspaces with one lockfile.
- Build approach: pnpm workspace scripts first; do not add Turborepo until repository scale proves it useful.
- Unit/integration tests: Vitest 5.
- UI verification: manual only in a real browser and on real devices; do not use Playwright, browser automation, or another automated UI-testing runner.
- Property-based tests: fast-check for descriptor validation, deterministic encoding and parser invariants.
- Versioning/release management: Changesets with semantic versioning.
- CI: none. Verification and release gates run locally with Node 24 and locked dependencies; do not add GitHub Actions workflows.
- Dependency updates: Renovate weekly; security updates may bypass the weekly window.
- V1 PDF generation uses Puppeteer only as a server-side document renderer; it is not used to test UI changes. PDFKit, Playwright PDF generation and pdf-lib adapters are V2 work and likewise require manual verification for any user-facing UI.
- V1 PDF signatures target PAdES Baseline B-B through the Dockerized DSS 6.5 reference adapter. PAdES Baseline B-T is available only when an RFC 3161 TSA is configured.
- V1 paper transport is `CRD1:` + Base45 (RFC 9285), containing deterministic CBOR (RFC 8949) and COSE_Sign1 (RFC 9052), signed with ES256/P-256/SHA-256, QR error correction M.
- The maximum V1 COSE object size before Base45 transport is 1200 bytes. Oversized payloads fail closed; claims are never silently dropped.
- V1 claims are a flat map containing only strings, booleans and safe integers. Floating-point values, arrays, arbitrary nested objects and binary values are rejected. Money uses integer minor units plus an explicit ISO currency code.
- `issuedAt` is RFC 3339 in the TypeScript API; compact paper encoding may use epoch seconds.
- `statusUrl` is optional and must use HTTPS outside local development. `artifactDigest` is generated by the digital-artifact pipeline rather than manually supplied to the primary `sealPdf` flow.
- Production APIs never handle raw private-key bytes. Local development keys are explicit development tooling and are untrusted outside the demo trust store.
- Cryptographic validity and issuer trust remain separate. Verdicts are `VALID_TRUSTED`, `VALID_UNTRUSTED`, `INVALID` and `UNVERIFIABLE`; lifecycle is separate (`ACTIVE`, `REVOKED`, `CANCELLED`, `SUPERSEDED`, `EXPIRED`, `UNCHECKED`).
- Browser printing reports `PAPER_CLAIMS_ONLY`; it never claims `DIGITAL_ARTIFACT_SIGNED` for unknown OS print bytes.
- No private keys may enter frontend bundles, logs, fixtures or repository history.
- No mandatory Credaryn cloud service, global root CA, blockchain dependency, custom cryptographic algorithm, custom general-purpose trust envelope, OCR dependency in the cryptographic path, or invisible-watermark dependency may be introduced.
- All untrusted PDF, QR, CBOR, COSE, certificate, image and remote URL inputs receive explicit size and time limits before deep parsing. Parsers fail closed on unknown critical fields and algorithms.
- TDD is mandatory: RED → GREEN → REFACTOR for every behavior added to core, paper, PDF and verifier packages.
- Unit coverage target is at least 90% for core/paper/verifier packages and 100% branch coverage for security-critical validation and verdict code where practical.
- Golden vectors are committed for deterministic CBOR bytes, COSE signatures, Base45 payloads and complete QR text. Security fixes require regression tests before merge.
- Before V1 beta, manual testing covers at least two real printers, two phone cameras and one scanner. Results are recorded as a public compatibility corpus; no universal print/scan claim is made.
- Use Apache-2.0. Publish `SECURITY.md` before public beta. Generate an SBOM, use npm provenance/trusted publishing, sign/tag releases and keep publishing automation OIDC-based where possible.
- Stable 1.0 is blocked until the threat model, interoperability matrix, independent security review, PAdES independent validation and release gates are complete.

## Phase protocol: mandatory for every milestone

The following protocol is repeated for Phase 0 through Phase 12. The phase implementer must not skip a section or work ahead.

1. Write or update the phase acceptance criteria and the phase test matrix before implementation.
2. Write the smallest failing test for the first behavior and run it to record RED.
3. Implement only enough code to make that test GREEN.
4. Continue RED → GREEN for the remaining behaviors, then REFACTOR without changing the contract.
5. Run the phase-specific automated gates, then the repository gates that already exist.
6. Run the exact manual verification procedure in a clean working tree with the documented local services.
7. Record commands, results, screenshots or fixture hashes in `docs/verification/milestone-<N>.md`.
8. Stop. Do not implement, scaffold or merge the next phase until the user has inspected the result and explicitly says to continue.

### Required phase report

Every phase report must contain:

```markdown

## Manual check
- Record the environment, exact command or page, actions performed, expected result and observed result.
```

The report is evidence, not a substitute for actually running the check. A failed check stays failed until the cause is fixed and the check is rerun.
